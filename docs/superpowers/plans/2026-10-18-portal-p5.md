# Portal P5: Documents Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A portal client browses, opens and previews their own SAP quotations, orders, deliveries and invoices, limited to the fields the tenant's admin allows, with a link back to the project a document came from.

**Architecture:** One pure module (`portal/doc-fields.ts`) is the field rule: always/never/denylist/defaults and `portalSchema`, which cuts a cached B1 schema down to the admin's list. A portal `docs` router reads through it with the CardCode fence (`readRows`' `extraFilter`, a per-company cursor key, a CardCode check on single reads). The portal plugs `docs.*` into the existing `UiSource` seam, so `ListReport`/`ObjectPage`/`useDetailView` run unchanged. Admins pick fields in a new Settings → Portal tab, through the existing `ColumnsTab` p13n panel.

**Tech Stack:** Bun, oRPC, Drizzle (Postgres), zod v4, React + TanStack Router/Query, UI5 Web Components for React.

**Spec:** `docs/superpowers/specs/2026-10-07-portal-redesign.md`, §13.1 (P5), plus §8, §9, §13 and the P5 status note at the top.

## Global Constraints

- Bun only (`bun test`, `bunx tsc`). No new dependencies.
- Type-check per project: `bunx tsc -p <project>/tsconfig.json --noEmit` for `packages/{b1,config-engine,db,ui}`, `apps/{agent,server,web,portal}`.
- Imports use explicit `.ts`/`.tsx` extensions; `verbatimModuleSyntax` is on, so use `import type` for types.
- Schema changes ship via `bun run db:push` (Postgres on :5432 is up). New tables live in `packages/db/src/schema/portal.ts`, which is already re-exported.
- `// ponytail:` comments mark deliberate ceilings (name the limit and the upgrade path). Comments explain *why*.
- Portal entities are exactly `Quotations`, `Orders`, `DeliveryNotes`, `Invoices`.
- `ALWAYS = DocEntry, DocNum, DocDate, DocumentStatus, DocTotal, DocCurrency`; `NEVER = CardCode`; denylist = `*Cost*`, `GrossProfit*`, `GrossBuyPrice`, `StockPrice`, `StockSum*`, `*Margin*`, `U_CF_Key` (case-insensitive); defaults = header `DocDueDate, NumAtCard, Comments`, lines `ItemCode, ItemDescription, Quantity, UnitPrice, LineTotal`.
- Print is **Preview only** in both apps. No Download button anywhere.
- **No commits during execution.** The git index holds the user's own staged work, and a plain `git commit` would sweep it in. Commit only when the user asks, and then with explicit pathspecs.

## Review Focus

1. **A stored `docFields` naming a field that has since been denylisted or dropped from B1** (a removed UDF). The portal must never show it, and the page must still open. → Task 1 (unknown and denied names dropped) and Task 3 (stale setting test).
2. **A guessed DocEntry belonging to another company** on `one`, `print` or `project`. Must be `NOT_FOUND`, and the PDF never renders. → Task 3.
3. **A list cursor issued to company A, replayed by company B.** Must be `BAD_REQUEST`. → Task 3.
4. **B1 sending more fields than `$select` asked for** (the mock ignores `$select`; real B1 adds `odata.*` and UDFs). `rows` and `one` must still cut every row to the schema. → Task 3 (the mock returns full rows).
5. **An entity name outside the four** (`BusinessPartners`, `PurchaseOrders`). Must be refused by input validation before any SAP call. → Task 3.

```ts
// Base document type → the entity it names (DOCUMENT_FLOWS' codes, as doc-chain.ts walks forward).
const BASE: Record<number, DocEntity> = { 23: "Quotations", 17: "Orders", 15: "DeliveryNotes" };
// frontier starts at [{ entity, docEntry }]; up to 3 hops. A Quotations entry adds its docEntry to `found`.

// happens for Quotations too. The next frontier is the distinct { BASE[l.BaseType], l.BaseEntry }
// over its lines.
// ponytail: at most 10 documents per hop — raise it if one invoice ever gathers more base documents.
```
